## Problem Statement

Open Institutional Custody wants large OSS adoption and real credibility. The
stated target was "100k stars and crazy creds." For a security-critical custody
project, stars are a lagging vanity metric. The real currency is "who trusts you
with their money, publicly." The lever we chose: shorten time-to-first-successful
custody so builders can run the stack themselves in about 5 minutes, then talk
about it.

## What Makes This Cool

A builder clones nothing and configures nothing, yet in minutes they watch the
system refuse to get robbed: an attacker swaps the destination after approval and
the independent signer refuses to sign. Then they see the honest path settle: an
EVM transfer (dev single-key secp256k1) and a Solana 2-of-3 FROST transfer, with
the receipt and audit log. That is the entire "Your rules. Before the signature."
thesis, demonstrated, not asserted. Most "wallet" demos show a balance. This shows
multi-party verification that no single key could bypass, and a blocked theft that
proves it. That difference is the whoa.

Chain accuracy: only Solana uses FROST 2-of-3 threshold signing. The EVM demo path
uses the development single-key secp256k1 backend. The GIF narration and copy must
never imply the EVM transfer is threshold-signed.

The credibility flywheel this unlocks (each crowd is the key to the next):
- Security researchers respect the code and threat model.
- That respect de-risks self-hosting for builders, who run it and blog about it.
- Builders running it in the wild de-risks a lighthouse treasury deployment.
- The deployment plus the RFCs make the standards crowd cite protocol-v1.

The same small set of artifacts serves all four crowds. The quickstart is the
first one.

## Constraints

- Current full-stack self-host is not 5 minutes. It needs Rust 1.95, mold, CMake,
  a C/C++ toolchain, compiles ~363 tests, and the docs record disk-space failures
  on the default profile.
- `scripts/local-stack/bootstrap.sh` prompts for a 12-byte passphrase and the flow
  wants multiple terminals. Every prompt and extra terminal is a drop-off.
- Project is a development preview. Real funds never move; simulators only.
- Security guardrails in docs/local-stack.md forbid real keys in any hosted demo.
  The demo path must use ephemeral dev keys and be clearly labeled simulated.
- `OIC_CONSOLE_DEMO=1` already disables the console's live custody bridge. Reuse it.

## Premises

All four confirmed by the builder with no pushback:
- P1. The adoption bottleneck is time-to-first-successful-custody, and
  "clone + cargo build" cannot hit 5 minutes. Ship prebuilt.
- P2. "It just worked" means zero external accounts and zero prompts on the demo
  path. Real security lives behind a separate `--production` path.
- P3. The quickstart must end on the whoa (approve, independent verify, FROST
  settle, receipt, audit log), not "listening on :8787."
- P4. Stars come from the README. A 20-second asciinema/GIF at the top delivers
  the whoa without running anything.

## Approaches Considered

### Approach A: `oic demo` one prebuilt binary (minimal viable)
Ship release binaries via GitHub Releases (cargo-dist). Add a `oic demo` command
(or `curl ... | sh`) that boots the stack with baked-in dev defaults, no
passphrase prompt, one terminal, runs an EVM and a Solana 2-of-3 transfer, and
prints the receipt, audit log, and a short "what just happened" explainer.
Effort S/M, risk Low. Reuses scripts/local-stack, oic-approve, release binaries.

### Approach B: `docker run` full stack + console (ideal architecture)
One `docker run ... ghcr.io/.../oic-demo` boots coordinator, signer network, and
the Next console in demo mode, seeds a demo vault, and opens the browser to the
approve-verify-settle flow with an audit-log view. Effort M/L, risk Med. A pinned,
verifiable image digest is itself a security flex. Reuses scripts/local-stack,
console demo mode, brand assets.

### Approach C: hosted sandbox + README GIF (ruled out as the primary)
Hosted simulated sandbox plus a README GIF. Ruled out as the lead because a hosted
custody demo walks a trust tightrope the docs warn against, and it is not
self-host. Its GIF, however, is cheap and high-value, so it is folded into Phase 1.

## Recommended Approach

Two-phase plan, rebalanced after eng review.

Phase 1 (maximum reach from day one): the `oic demo` CLI AND a Docker image.
- Native prebuilt binaries for macOS (arm64 + x86_64) and Linux x86_64, so the
  quickstart runs on the majority machine, not Linux only (review D4).
- A Docker image for anyone without the toolchain, so there is a path on every OS.
- The demo runs both the blocked-theft scene (lead) and the honest settle (review
  D3), prints the receipt and audit log, and ends on the whoa.
- The README GIF leads with the blocked theft.

Phase 2 (the visual layer): the Next console in demo mode (`OIC_CONSOLE_DEMO=1`)
opening the browser to the approve-verify-settle flow with an audit-log view, and
a pinned, verifiable GHCR digest. This is the screenshottable artifact; it is not
on the critical path for the first swing.

Rationale: the quickstart's whole job is "run it yourself in five minutes," so it
has to work on the machine the audience actually has. Native binaries give the
fastest first run; the Docker image guarantees a path everywhere. C's hosted demo
stays deferred until the security story and infra guardrails are ready.

Phase 3 (adoption engine, GATED on Phase 1 shipping + the 5-minute clock measured).
Four expansions accepted in CEO review, each specified here so they are real scope,
not a wish. They do not block the Phase 1 first swing; they layer on after it ships.
- Codespaces one-click sandbox: a devcontainer + "Open in Codespaces" README button.
  It downloads and runs the Phase 1 PREBUILT binary or Docker image (never a source
  build, which can't hit 60s per the Constraints), so it is real self-host, distinct
  from the deferred hosted-custody Approach C. Verify: button boots the demo in ~60s.
- Release provenance: ship GitHub build provenance / SLSA attestation on releases NOW
  (easy, GitHub-native), alongside the Phase 1 SHA-256 checksums + minisign/cosign
  signature (it adds to them, does not replace them). Reproducible builds for Rust are
  a SEPARATE, harder milestone tracked on their own, not a casual badge.
- "Custody in CI" GitHub Action: a composite action wrapping `oic demo --check` that
  runs the blocked-theft + settle assertion in a user's CI. Inputs: none required;
  output: non-zero on a theft that would have settled. Verify: a sample workflow fails
  when the guard is removed.
- Threat model + bug bounty: ship THREAT_MODEL.md + SECURITY.md + a hall-of-fame NOW
  (no real funds move in dev preview, so a PAID bounty is premature). The paid tier is
  deferred to the first lighthouse deployment with real value at stake.

## Open Questions

- What is the exact end-state "receipt" we print? It should name the policy,
  the independent approver, the threshold used, and the audit-log path, in plain
  language a non-Rust reader understands.
- Which OS targets ship binaries first? Linux x86_64 is certain. macOS needs
  notarization work; decide whether to delay or ship unsigned-with-instructions.
- Decided (review D1/D2): `oic demo` ships as a NEW top-level `oic` CLI crate (the
  owner's choice for a dedicated front door). Decided (review, from eng findings):
  the crate WRAPS `services/local-stack`'s in-process library (`Stack`, `bootstrap`,
  `InProcessSigner` in src/lib.rs) directly, the same path `tests/money_loop.rs`
  exercises. It does NOT shell out to bootstrap.sh/start.sh, which would re-introduce
  the bash + jq dependency and the passphrase prompt the demo removes. The `oic`
  binary also absorbs `start`/`bootstrap` subcommands so the front door leads
  somewhere real, not a dead end.
- For Phase 2, Dockerfile base and whether to publish a multi-arch image on day one.

## Success Criteria

- A new user on a clean macOS or Linux machine (or via Docker on any OS) runs one
  command and sees: (1) a blocked theft — a destination swapped after approval is
  refused by the independent signer; (2) a settled EVM transfer (dev single-key);
  (3) a settled Solana 2-of-3 FROST transfer. The blocked theft plus one settled
  transfer is the acceptance minimum; all three are the target.
- The 5-minute clock is measured end to end, including binary download on a
  typical connection, not just runtime. State the download size in the README so
  the headline promise and the measured number use the same clock.
- Zero external accounts, zero secret files, zero prompts on the demo path.
- README opens with a <=20s GIF that LEADS with the blocked theft, then the settle.
- The command exits on the whoa: receipt + audit log + one-line explainer.
- An E2E test covers `oic demo`: it exits 0, blocks the theft, settles both chains,
  and emits receipt + audit log. It reuses the assertions in money_loop.rs.

## Distribution Plan

- Phase 1 native binaries: GitHub Releases via cargo-dist. CI builds on tag push
  (GitHub Actions matrix: macOS arm64, macOS x86_64, Linux x86_64 — review D4).
  The `oic demo` subcommand needs no accounts or RPC.
- Phase 1 Docker image: publish to GHCR on the same tag so every OS has a path.
  Pin and publish the digest; document "verify the hash" as a security feature.
- Phase 1 integrity (not deferred): publish SHA-256 checksums and a minisign or
  cosign signature for every release artifact. The README headline is "download,
  verify the signature, then run"; `curl ... | sh` is offered as a convenience
  fallback, not the headline, because the security-researcher audience distrusts
  piping a remote script into a shell (review, outside voice #6). The installer
  verifies the checksum before it runs the binary.
- Repo identity (blocker, fix before cargo-dist bakes URLs): reconcile the canonical
  org and the spelling. `Cargo.toml` `repository` = `github.com/etofdn/...`;
  README/plan say `0xTheSingularity/...`; the name is misspelled `insitutional` in
  the repo field and `insititutional` in the working-dir name. cargo-dist derives
  installer and release URLs from `repository`, so decide org + spelling first;
  renaming after a release breaks installers and image tags.
- MSRV: the workspace declares `rust-version = "1.85"` but CI pins 1.95.0 and the
  stack needs 1.95. Set a consistent MSRV before the release/build-from-source path.
- README GIF generated with asciinema + agg (or vhs), committed under docs/assets.
- CI/CD: extend the existing .github workflows; add a release workflow keyed on
  version tags.

## Dependencies

- A top-level `oic` CLI entry point (new crate or extend oic-approval-client).
- A demo-mode flag through bootstrap/start that skips the passphrase and uses
  ephemeral dev keys, isolated from the production path.
- cargo-dist setup and a signing/notarization decision for macOS (Phase 1 scope).
- Dockerfile and console demo wiring for Phase 2.

### R1-1 — consistency (minor)

**Problem**

> The demo's chain scope is stated inconsistently. Approach A ('runs an EVM and a Solana 2-of-3 transfer') and Next Steps #1 ('one EVM + one Solana 2-of-3 transfer') commit to exercising both chains, but Success Criteria describes only 'a settled 2-of-3 transfer' (singular), leaving the acceptance bar ambiguous about whether one chain or both are required.

**Remedy**

> Make Success Criteria name the same chain scope as the committed approach (both EVM and Solana), or state explicitly that one settled transfer is the acceptance minimum and both chains are the target.

### R1-2 — clarity (minor)

**Problem**

> The `oic demo` crate-location item is listed under Open Questions yet asserts its own answer in the same sentence ('A single top-level `oic` binary is the better front door'), and the same choice reappears under Dependencies. Presenting a stated preference inside Open Questions blurs whether this is decided or still open for the next review.

**Remedy**

> Either record it as a decision with its rationale (single top-level `oic` binary) outside Open Questions, or keep it genuinely open without asserting the answer.

### R1-3 — clarity (minor)

**Problem**

> The headline '5-Minute Self-Host Quickstart' and Problem Statement ('run the stack themselves in about 5 minutes') use a different clock than Success Criteria, which measures 5 minutes with 'build/download time excluded'. For a prebuilt full-stack binary the download can be substantial, so the advertised promise and the measured criterion are not the same metric.

**Remedy**

> Align the headline promise and the measured criterion on one clock, or state the expected download-time budget separately so the 5-minute claim is unambiguous.

### R1-4 — completeness (minor)

**Problem**

> The Phase 1 `curl ... | sh` installer and GitHub Releases binaries have no stated integrity-verification story, while Phase 2 commits to a pinned digest and documenting 'verify the hash'. For a project whose entire thesis is security credibility with researchers, the Phase 1 install path omits any checksum or signature verification.

**Remedy**

> Specify a Phase 1 integrity check (published checksums/signatures for the release binaries) or explicitly note why verification is deferred to Phase 2.
